# Configuration

All runtime configuration is a single Pydantic `BaseSettings` class.

## The settings class

`src/flow_agent/configurations/config.py`:

```python
class Settings(BaseSettings):
    model_config = SettingsConfigDict(
        env_file=".env",
        env_file_encoding="utf-8",
        case_sensitive=True,
        extra="ignore",
    )
    ...

settings = Settings()
```

- `env_file=".env"` — values are read from `.env`.
- `case_sensitive=True` — an environment variable must match the field name exactly.
- `extra="ignore"` — unrelated environment variables do not raise.

A module-level `settings` instance is imported throughout the codebase.

## The singleton caveat

Because every module does `from ...config import settings`, changing configuration in a test means patching the reference in **each importing module**:

```python
with patch("src.flow_agent.graph.settings", custom), \
     patch("src.flow_agent.utils.nodes.settings", custom), \
     patch("src.flow_agent.llms.LangChainChatLLM.settings", custom):
    ...
```

This is a known design smell. Passing a `Settings` instance as a parameter, or exposing a `get_settings()` accessor, would remove the need for the multi-module patch.

## Pitfalls

- **Security defaults are off.** `IS_PII_REDACTION_ENABLED` and `IS_INPUT_VALIDATION_ENABLED` both default to `False`, so the safety layers are opt-in.
- `ENABLE_LANGSMITH_TRACING_V2` is a **string** (`"false"`), not a boolean, and is assigned straight to an environment variable.
- `Settings()` is constructed at import time, so `.env` must be readable (or every field must have a default) before the module imports.
- The model settings exist for every provider even if that provider is never selected; changing a distribution does not remove the need for the corresponding API key.
